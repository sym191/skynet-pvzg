## 范围约束

- 保持上游 Lua 的可观察接口、消息及失败语义；内部采用 C++23、RAII、明确所有权与线程边界。
- 核心运行时和网络继续由重构实现承担；成熟算法及 C 薄绑定可按模块复用并单独验收。
- C ABI 目标是同一工具链、bundled Lua 下重新编译模块可链接，不承诺任意现成 `.so` 二进制兼容。
- UDP IPv6 与 IPv6 地址 blob 延期，已有 TCP IPv6 保留并回归；不在本轮规划中自动恢复延期范围。
- 自定义 `SOCKET_BUFFER_OBJECT`、普通文件 FD 等已有未支持项进入发布限制表；如业务必须使用，需先补专项任务。
- 阶段六不包含业务数据库、玩家分片、跨节点登录唯一性或组队文件多进程写入；多节点测试使用独立状态目录。
- TLS 作为阶段七可选构建能力，启用时必须验收；未启用时明确标识。

## 推进顺序与交付规则

1. 阶段六先固定协议与测试拓扑，再完成 harbor、cluster，最后统一混部与故障验收。
2. 阶段七先处理模块加载和分配器，再做共享数据、工具模块及运维。无依赖的工作可以独立推进；共享结构必须等待生命周期契约固定。
3. 阶段八的差分和数据采集规范从阶段六开始使用，最终集中完成长稳、性能和发布检查。
4. 每个任务形成可独立审查的提交，包含实现、对应测试与支持矩阵更新。以下各文档的提交主题是未来开发建议，本次仅提交规划。
5. 阶段完成记录必须列出代码 SHA、测试环境、命令、结果、日志位置和已知限制；跳过或宿主不支持的检测不能标为通过。

本计划采用依赖与完成门槛排序，不在缺少负责人、环境和基线数据时承诺工期。
阶段六的协议审计、阶段七的 Lua 补丁/分配器审计完成后，再按实际任务量安排迭代。
